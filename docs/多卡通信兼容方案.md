## 默认 NCCL 路径的问题

| 实际平台实例 GPU 组合 | 默认 NCCL all-reduce |
| --- | --- |
| 6、7 | 超时 |
| 3、4 | 通过 |
| 4、5 | 超时，已捕获完整诊断 |

GPU 0–3、4–7 分别位于两个 NUMA 域，同域拓扑为 PIX，跨域为 SYS。NVLink 全部 inactive，不能声称这台机器存在可用 NVLink。NVML 虽报告 peer 能力 OK，实际通信失败时内核记录对应 b1/b2、b4/b5 GPU 的 DMAR DMA Write fault，原因为 PTE Write access is not set。相应 PCIe 上游桥的 ACS ReqRedir/CmpltRedir 均开启。

证据指向 IOMMU/ACS 与 PCIe peer DMA 路径冲突。该问题与先前已修复的 NVML/驱动版本不匹配不同；本次未据此卸载、升级或重装驱动，也未修改 BIOS、PCIe 寄存器、内核启动参数或再次重启。

## 已批准的实施方式

为此新环境的**新建实例**默认注入 `NCCL_P2P_DISABLE=1`，保留原镜像和框架版本，随后用网站新建实例重验双卡 NCCL、快照重建和资源释放，再公开标准镜像。

实现范围：后端增加默认关闭的站点配置，创建操作冻结该值，WorkloadSpec 根据冻结值生成该环境变量；新环境私有 backend.env 设置为开启。旧部署默认行为保留，正在运行的实例不原地修改。相关代码和配置在验证通过后记录到部署文档。

影响：多卡通信改走后备路径，可能降低带宽、增加主机内存及 CPU 通信开销；当前未测量性能损失。该设置不修复底层 PCIe/IOMMU，也不能保证用户自行使用其他通信库时不会触发同类问题。不开启全局 IOMMU/ACS 改动，不需要主机重启。

回退：关闭该站点配置并重启 API，仅后续新建实例恢复默认 NCCL 路径；已创建实例按原冻结配置保留。回退前仍需确认底层 P2P 是否已修复。

另一条路线是维护 IOMMU/ACS 配置以恢复硬件 P2P 性能，需要进一步核验 DMA 隔离、虚拟化及 PCIe 桥配置，提出具体启动参数/BIOS 方案；涉及重启或隔离变更时单独确认。本轮没有实施此路线。
