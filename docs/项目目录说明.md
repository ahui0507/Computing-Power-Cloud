# 项目代码结构

项目采用模块化单体。前端提供用户界面，后端编排资源申请和实例运行，K3s 负责实际容器与 GPU 调度。

```text
frontend/src/
  api/                      按业务拆分的接口客户端
  views/                    页面
  components/               通用界面组件
  stores/                   共享界面状态
  types/                    前端接口类型
  utils/request.ts          HTTP 请求与错误转换
backend/
  app/
    routers/                HTTP 参数、鉴权依赖、响应契约
    schemas/                请求与响应模型
    services/               业务编排和状态转换
    infrastructure/kubernetes/
      client.py             独立集群连接
      manifests.py          Pod、Service、Ingress 模板
      gateway.py            集群创建、查询与删除
    models/                 ORM 与枚举存储约定
    core/                   配置、数据库、认证、审计、异常边界
    assets/                 实例环境检查、训练起步脚本
  alembic/versions/          已冻结的数据库版本迁移
  tests/                    业务、接口、集群适配器和迁移回归测试
  scripts/                  数据初始化与运维排障
deploy/kubernetes/
  backend/                  后端 Deployment、Service、RBAC
  cluster/                  GPU 插件、命名空间和存储配置
deploy/storage/             数据卷准备、原生配额 helper、备份配置及定时器
scripts/                    统一迁移入口、在线快照备份、隔离恢复验证
test-images/                GPU 开发环境测试镜像
docs/                       维护与部署说明
API.yaml                    从后端导出的当前接口契约
```

## 模块职责

路由通过 Pydantic 校验参数和输出，将业务调用交给服务；异常由全局处理器转换成统一内容和真实 HTTP 状态。路由不吞掉业务异常。

`SchedulerService` 负责申请身份、GPU 预留与释放入口。申请使用用户范围内的 `Idempotency-Key` 和参数摘要，唯一请求记录先于 GPU 预留写入，同一请求重试返回原申请；同一标识改变参数返回 409。`ResourceService` 的预留和回收方法只修改数据库及 flush，由业务操作统一提交。

`OperationService` 执行数据库中持久化的创建/释放操作。预留、实例记录和创建意图在一个事务中提交，集群调用在事务提交后执行。操作通过租约协调多个执行器，按申请、操作记录的顺序加锁；释放失败保留重试时间、计费截止时间和 GPU 预留。

`ReconciliationService` 在后台恢复待执行或租约过期的操作，并分批轮转核对实例。集群无法连接时保留预留和最后确认状态；只有确认 Pod 不存在或进入终态后才安排清理。核对范围是数据库登记的申请，不扫描删除集群中的未知对象。

`InstanceService` 负责运行时间、状态映射和响应投影。普通实例列表读取数据库，诊断参数 `refresh=true` 使用与后台一致的核对规则。远程查询结束后重新检查数据库状态，防止并发释放的实例被旧快照改回运行中。

`AccessService` 使用申请时保存的访问配置计算地址。创建配置包含命名空间、节点、镜像命令、Ingress 和工作目录参数，后续配置变化不会改变已有操作的目标；令牌由持久化平台密钥派生，不写入操作日志。Kubernetes 适配器只接收运行参数，不查询业务数据库；同步集群请求在线程中执行，并设置网络超时。

前端 API 按认证、资源、容器、镜像、存储、集群、计费与管理拆分，`api/index.ts` 保持统一导出。HTTP 层不导入路由或认证 Store；应用入口连接 401 处理、认证状态清理和登录页导航。

v0.2.0 控制台增加 `components/` 中的公共页面、异步状态、实例列表和认证上传组件，`composables/` 集中管理会话资源、轮询、时钟及页面请求。私人 Store 在账号切换时统一清理，并拒绝迟到响应覆盖新账号。账户设置、真实任务与审计接口分别由 `routers/console.py`、`routers/jobs.py` 和 `services/job_service.py` 支持，详见[前端控制台架构与验收](前端控制台架构与验收-2026-10-10.md)。

## 实例状态与资源回收

| 集群与业务情况 | 前端状态 | GPU 预留 |
|---|---|---|
| Pod 已提交但尚未 Ready | pending | 保留 |
| Pod Running 且 Ready | running | 保留 |
| 工作负载自然结束 | stopped | 后台清理确认后回收 |
| 创建失败且清理已确认 | failed | 回收 |
| 创建失败且清理未确认 | failed | 保留，可重试释放 |
| 已接受释放，删除或结算仍在恢复 | releasing | 保留到删除与结算确认 |
| Pod 删除已确认并完成数据库回收 | released | 回收 |

运行开始时间来自 Pod 中容器的实际启动时间，Jupyter 的 Ready 条件决定是否提供交互入口。首次 Ready 时间单独持久化，已经运行过的实例短暂失去就绪状态不会被当作首次启动超时清理。接口只为运行中的实例提供带独立令牌的连接地址。

集群创建调用尚未完成时，申请保持 `pending`，释放请求返回 409；完成提交后进入 `approved`，允许释放。若进程中断，后台在租约过期后恢复同一操作。已有同名资源需核对申请/用户归属及 Pod 的镜像、节点、GPU 数、鉴权和工作目录配置，才可接续使用。

释放入口先持久化计费截止时间，再获取运行时间并删除集群资源；删除确认后在同一事务中提交账单、余额、实例终态和 GPU 回收。删除成功但结算提交失败时，重试沿用原截止时间。执行语义为可重试的至少一次调用，通过对象命名、操作唯一约束、租约与幂等结算避免重复占用和重复扣费。

当前 `gpus` 记录用于预留节点内的逻辑名额。Pod 被约束到选定节点，具体物理 GPU 由 NVIDIA device plugin 分配；指定物理 UUID 或同节点混合 GPU 型号的调度需要后续专门实现。

工作目录采用共享 ReadWriteMany PVC，后端与实例共用用户子目录，实例只挂载自己的目录。支持按小时、包日、包周申请，套餐下单扣费、就绪起算。暂停、恢复、重启及改变现有实例 GPU 数量尚未实现，相关接口明确返回 501。

## 本地验证

后端使用 Python 3.10，与 `requirements.txt` 的固定版本保持一致：

```bash
cd backend
python -m pip install -r requirements-test.txt
python -m pytest
```

测试使用内存 SQLite 和替代集群客户端，通过独立配置禁止读取部署 `.env`，并启动真实本地 Jupyter 验证令牌、文件读写与 WebSocket 执行。MySQL 并发与真实 GPU/NFS/Ingress 仍需在集成环境验证。

```bash
cd frontend
npm ci
npm test
npm run build
```

更新后端接口后，在仓库根目录运行 `python backend/scripts/export_openapi.py` 重新生成 `API.yaml`。数据库维护见 [数据库迁移](数据库迁移.md)，部署入口见 [部署目录](../deploy/README.md)。

完整启动和验收步骤见 [MVP 部署与验收](MVP部署与验收.md)。

## v0.7 模块边界

新增功能保持原有模块化单体结构。`core/audit.py` 是唯一审计写入入口，服务层不再依赖 HTTP 路由；文件夹接口归入 `routers/storage.py`，原 URL 保持兼容。认证请求共用邮箱校验，Pydantic 配置统一采用 v2 写法。

| 责任 | 代码入口 |
| --- | --- |
| 用户存储份额、全局空间限制及错误转换 | `services/storage_quota_service.py`、`deploy/storage/platform_storage.py` |
| 文件路径校验与原子上传 | `services/storage_service.py` |
| 站内提醒生成、去重、过期 | `services/notice_service.py`、`routers/notices.py` |
| 实例 CPU/内存采样与退出原因 | `infrastructure/kubernetes/runtime_metrics.py` |
| 自检与训练示例 | `services/environment_service.py`、`app/assets/` |
| 管理员运维状态投影 | `services/maintenance_service.py` |
| 备份与独立恢复验证 | `scripts/backup_snapshot.py`、`scripts/verify_backup_recovery.py` |

前端页面组织导航和展示，`StorageCapacity`、`TrainingExample`、`InstanceDiagnostics`、`InstanceTelemetry` 分别负责一个功能。通知 Store 复用会话资源管理，退出或换账号会清理数据并丢弃旧账号迟到响应。通用页面加载、刷新和错误提示继续复用既有 composables，避免为新页面另建一套状态逻辑。

运维临时脚本、服务器凭据、构建依赖和备份不进入仓库。当前架构以本文件和工作环境存储架构为准，日期命名的验收记录用于追溯历史版本；迁移步骤集中在平台迁移手册及 `deploy/storage/README.md`。

## v0.8 管理员统一开通账号

管理端 `POST /admin/users` 校验并归一化邮箱，调用 AdminService 在同一事务中创建普通用户、初始化个人目录和存储额度、写入审计。初始密码规则集中在 core/security.py，普通账号和首次安装管理员一致；账号密码仅保存哈希，重复创建不会重置密码。前端 CreateUserDialog 只接收邮箱，Profile 沿用原改密流程。注册页面、客户端注册方法、验证码和发信服务已移除；旧 `/register` 网页重定向登录，旧注册及验证码 API 固定返回 403。

## v0.9 临时工作区与共享终端环境

`core/workspace.py` 定义新旧布局；创建操作将布局冻结到 JSON，Kubernetes 模板、实例投影、SSH 信息和任务启动/取消均按该冻结值取路径。新实例的个人 NFS 目录只挂到 /data，/workspace 保留在独立可写系统盘，避免空卷排除工作文件导致保存镜像丢失工作区。`infrastructure/kubernetes/shell_runtime.py` 生成统一 Bash 配置和 SSH/SFTP 会话包装器，运行配置放临时 emptyDir。旧创建参数保持兼容。前端 InstanceStorage 独立展示两类目录和保存示例，释放确认与文件页同步其保留规则。
