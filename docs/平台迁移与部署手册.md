# 平台迁移与部署手册

统一入口为 `scripts/platform_ops.py`，使用 Python 3.8+ 标准库，可在现有 Ubuntu 20.04 的系统 Python 上运行。后端及数据库盘点使用已安装依赖的后端 Python 3.10 环境。此工具面向当前已验收的 Linux amd64、MySQL、Nginx、K3s 和 NVIDIA 架构。配置模板为 `deploy/migration/site.example.json`。

已完成的真实演练和验证边界见 [迁移工具验证](迁移工具验证-2026-10-11.md)。

## 文件与职责

| 内容 | 管理方式 |
| --- | --- |
| 新服务器 IP、域名、目录、用户、节点 ID、Traefik 端口 | 一份站点 JSON，`render` 生成所有相关配置 |
| 业务密码、平台密钥、镜像代理令牌 | 独立 `backend.env`，不进 Git；本工作区密码仍按根目录本地凭据约定管理 |
| 每节点监控令牌 | 独立 JSON，以原数据库节点 ID 为键；从各节点原 `/etc/platform-monitor.env` 收集 |
| 源码与前端产物 | `package` 从干净 Git 提交构建，记录完整提交 SHA 和文件校验值 |
| 数据库、个人文件、个人镜像及运行时配置 | `backup` 生成独立迁移备份；`verify` 校验；`restore` 仅向空目标恢复 |
| 公共基础镜像 | 从实际有完整缓存的计算节点 `export-images` 导出，不能只搬控制节点的不完整镜像标签 |
| 节点地址调整 | `rebind` 保留原 ID、硬件 UUID、资源池及历史外键，仅更新主机名和地址 |

生成文件、SQL、依赖、OCI 镜像和密钥不放进仓库。建议在服务器 `/srv/platform-migration/` 操作；若在本地准备，使用被忽略的 `.migration-local/`。不要将私有配置写进示例文件。

## 迁移边界和前置条件

此次准备工具，不会自动切换现有服务器。完整迁移采用停机方式：先通知用户保存代码和环境，等待个人镜像 ready，结束所有实例和镜像任务，然后停止后端。不能迁移运行中的进程、CPU/GPU 内存、未保存的容器系统盘；后台任务文件随个人工作目录保留。

迁移工具不会安装或替换 GPU 驱动、重装 K3s、自动改网卡、NAT 或防火墙。这些依赖与硬件、网段有关，需先在新节点准备。当前 K80 使用 470 系列驱动，已验收集群为 `v1.33.6+k3s1`、Python 3.10.15；已有基础镜像建议直接导入，避免下载站或新版软件改变兼容性。新硬件使用其支持的驱动，不盲目沿用 K80 驱动。

在 Ubuntu 22.04 新控制节点可先安装以下基础依赖；Ubuntu 20.04 应单独准备 Python 3.10，不能直接使用其系统 Python 3.8：

```bash
sudo apt-get update
sudo apt-get install -y python3.10 python3.10-venv nginx mysql-server redis-server nfs-kernel-server nfs-common git
```

计算节点需有 `nfs-common`、NVIDIA 驱动、Container Toolkit、K3s，以及代理所需的 `ctr`、`crictl`、`python3`。安装 K3s 时固定版本，加入新控制节点，不把旧集群 kubeconfig 直接当新集群凭据。安装单套 GPU 插件及 NVIDIA RuntimeClass，见 `deploy/README.md`；节点名须与站点 JSON 一致。

源和目标尽量保持服务用户的数值 UID 及 `workspace_gid`，恢复保留数值属主和目录权限。工具拒绝直接改变共享 GID；确需改 UID/GID 时，单独核对并转换存储权限。迁移版不处理 ACL/扩展属性，当前平台共享目录使用 Unix 属主、组继承和权限位。

## 1. 准备站点配置和源码包

从模板复制一份私有站点配置，修改所有节点地址和目录。已有系统迁移时，节点 `id` 必须来自数据库盘点；模板中的 1、2 不能当作现场事实。`control.ip` 是数据库登记地址，`control.nfs_ip` 是计算节点挂载 NFS 时使用的地址；两者可以不同。`public_url` 用校园网可访问的地址；Traefik NodePort 从新集群查询。

```bash
mkdir -m 700 -p /srv/platform-migration
cp deploy/migration/site.example.json /srv/platform-migration/source-site.json
kubectl get svc traefik -n kube-system
python3 scripts/platform_ops.py inventory --backend /home/REPLACE_SERVICE_USER/platform-current/backend --output /srv/platform-migration/inventory.json
```

站点模板沿用 HTTP 80 校园网部署；已有 HTTPS 站点应另外恢复证书和 Nginx TLS 配置，并同步后端 `INGRESS_USE_TLS`、入口地址和代理设置。本入口当前不会自动生成 TLS 或非标准网站端口配置。

可在各节点先运行只读前置检查，例如 `python3 scripts/platform_ops.py preflight --site /srv/platform-migration/target-site.json --node control --python /usr/bin/python3.10`。计算节点把 `--node` 换成对应名称。缺失依赖会明确标出。

在干净的 Git 发布提交上安装前端依赖并测试，再打包。`package` 会重新构建前端，避免携带旧 dist。基础 Python 依赖版本已固定；前端使用 `package-lock.json`。

```bash
cd frontend
npm ci
npm test
cd ..
python3 scripts/platform_ops.py package --output /srv/platform-migration/release
python3 scripts/platform_ops.py verify --bundle /srv/platform-migration/release
```

离线部署时在同架构 Linux、Python 3.10 环境准备完整 wheels：`python3.10 -m pip wheel -r backend/requirements.txt -w /srv/platform-migration/wheels`，然后给 `package` 加 `--wheels /srv/platform-migration/wheels`。不能使用 Windows wheels；`backend/.venv` 也不能直接复制到新机器。

## 2. 导出公共镜像、收集监控配置

把站点 JSON 和只读盘点文件安全传到原计算节点，运行：

```bash
sudo python3 scripts/platform_ops.py export-images --site /srv/platform-migration/source-site.json --worker worker1 --inventory /srv/platform-migration/inventory.json --output /srv/platform-migration/public-images.tar
sudo python3 scripts/platform_ops.py export-images --site /srv/platform-migration/source-site.json --worker worker1 --inventory /srv/platform-migration/inventory.json --output /srv/platform-migration/public-images.tar --execute
```

只导出盘点中 ready 的公共非快照镜像；已下架镜像不导出。多节点缓存不同，应逐节点核对并导出需要的镜像。同时携带生成的 `.sha256`。公共环境构建源码在 `deploy/workbench/`，但重建还需 standalone Python 和 Linux wheels，因此迁移优先使用已经验收的完整缓存。

管理员收集各节点的 `/etc/platform-monitor.env`，保存到权限 700 的单独目录，以 `--extra-secrets` 包含进备份。另整理 `monitor-tokens.json`，格式为 `{"原节点ID":"已有令牌"}`。不要重新发令牌后仍恢复旧数据库中的 hash。镜像代理令牌已包含在原后端环境文件中。

## 3. 停机并备份业务数据

先完成用户保存和释放，确认未完成计数为零。暂停外部自动化写入，停止后端和原节点的监控、镜像代理服务。工具不会替用户结束实例，也不会自动停服务。

```bash
sudo systemctl stop computing-platform-backend
# 在所有节点分别执行：
sudo systemctl stop platform-monitor-agent
# 在计算节点执行：
sudo systemctl stop platform-worker-agent
```

在原控制节点执行，先预览，再实际生成备份。默认以 root 连接本机 MySQL，兼容 root socket 认证；其他连接使用 `--mysql-host`、`--mysql-port`、`--mysql-user` 及权限 600 的 `--mysql-defaults` 客户端配置文件，密码不放命令行。

```bash
sudo python3 scripts/platform_ops.py backup --site /srv/platform-migration/source-site.json --backend /home/REPLACE_SERVICE_USER/platform-current/backend --output /srv/platform-migration/backup --extra-secrets /srv/platform-migration/collected-secrets
sudo python3 scripts/platform_ops.py backup --site /srv/platform-migration/source-site.json --backend /home/REPLACE_SERVICE_USER/platform-current/backend --output /srv/platform-migration/backup --extra-secrets /srv/platform-migration/collected-secrets --execute
sudo python3 scripts/platform_ops.py verify --bundle /srv/platform-migration/backup
```

实际执行会再次核对未完成业务、服务工作目录和 MySQL 服务器 UUID。备份包含所有个人目录、隐藏的持久化密钥、个人镜像 OCI 和 `.jobs` 任务文件、后端 `.env`、SQL、盘点及原站点配置。`mysqldump` 保存业务表和触发器，不搬 MySQL 系统账户，也不搬额外存储过程/事件；平台当前不依赖这些对象。

备份目录含明文运行时凭据，仅管理员可读，通过 SSH/SFTP 等受控方式传输。迁移时需同时带上源码发布包、业务备份、公共镜像包和校验文件；GitHub 本身不能替代业务备份。

## 4. 恢复到新控制节点

准备新站点 JSON，创建新数据库和专用账户，准备**空**个人文件目录、镜像目录及密钥恢复目录，保持后端停止。备份中任何文件校验失败、目标目录非空或目标数据库已有表，实际恢复都会停止。

```bash
sudo python3 scripts/platform_ops.py restore --site /srv/platform-migration/target-site.json --bundle /srv/platform-migration/backup --secrets-output /srv/platform-migration/restored-secrets
sudo python3 scripts/platform_ops.py restore --site /srv/platform-migration/target-site.json --bundle /srv/platform-migration/backup --secrets-output /srv/platform-migration/restored-secrets --execute
```

恢复先在同一文件系统临时目录解包并核对路径，再导入 SQL，最后安装存储目录。恢复失败不自动清空数据库；部分导入的目标应保留排障，使用另一个空数据库重试。恢复后的服务保持停止，避免旧操作在新集群误执行。

修改 `restored-secrets/backend.env` 中的 `DATABASE_URL` 为新数据库连接，保留原平台密钥和镜像代理令牌。源数据库地址不会自动成为新数据库地址。收集的监控配置按原节点 ID 整理成令牌 JSON。

```bash
sudo python3 scripts/platform_ops.py render --site /srv/platform-migration/target-site.json --backend-env /srv/platform-migration/restored-secrets/backend.env --monitor-tokens /srv/platform-migration/monitor-tokens.json --output /srv/platform-migration/generated
sudo python3 scripts/platform_ops.py install-control --site /srv/platform-migration/target-site.json --bundle /srv/platform-migration/release --generated /srv/platform-migration/generated --python /usr/bin/python3.10
sudo python3 scripts/platform_ops.py install-control --site /srv/platform-migration/target-site.json --bundle /srv/platform-migration/release --generated /srv/platform-migration/generated --python /usr/bin/python3.10 --execute
```

安装为新发布 SHA 建独立虚拟环境，支持离线 wheels；安装 NFS/PVC、Nginx、systemd，更新站点指定的入口软链接，后端保持停止。此前应创建 service_user/service_group，并允许该用户读取新集群 kubeconfig；可用专属组授权读取，不设成全局可读。站点 namespace 非 default 时先创建命名空间。

进入新后端执行数据库检查及节点地址重绑（以下路径替换成 target-site 中的 current_link）：

```bash
cd /opt/computing-platform/current/backend
sudo -u control .venv/bin/python scripts/init_db.py
sudo python3 /opt/computing-platform/current/scripts/platform_ops.py rebind --site /srv/platform-migration/target-site.json --backend /opt/computing-platform/current/backend
sudo python3 /opt/computing-platform/current/scripts/platform_ops.py rebind --site /srv/platform-migration/target-site.json --backend /opt/computing-platform/current/backend --execute
```

节点重绑仅适用于相同登记硬件迁址或更名。若更换 GPU，必须另外核对 UUID、型号和节点登记；不得伪造旧 UUID 或清空历史外键。资源池仍引用原 ID，个人镜像仍关联原节点 ID。停机迁移不重写历史订单曾用的接入地址。

## 5. 计算节点与代理

将仓库、generated 配置、公共镜像包、SHA256 及 inventory 传到新计算节点，确认它已经加入新集群且驱动/GPU 插件正常。安装会检查已有 fstab，遇到同挂载点的冲突配置会停止。

```bash
sudo python3 scripts/platform_ops.py install-agent --site /srv/platform-migration/target-site.json --generated /srv/platform-migration/generated --node worker1 --execute
sudo python3 scripts/platform_ops.py import-images --site /srv/platform-migration/target-site.json --worker worker1 --inventory /srv/platform-migration/backup/inventory.json --archive /srv/platform-migration/public-images.tar --execute
```

导入公共包，并把关联此原节点 ID 的 ready 个人镜像从 NFS OCI 归档导入 `k8s.io` 缓存。节点名称改了仍按原 ID 匹配。不要只拷贝 OCI 文件却漏掉 containerd 导入。

控制节点也安装监控代理，`--node` 换成 control 名称。随后在控制节点启动后端、重载 Nginx；各节点启动监控，计算节点启动镜像代理：

```bash
sudo systemctl enable --now computing-platform-backend
sudo systemctl reload nginx
sudo systemctl enable --now platform-monitor-agent
# 以下在计算节点执行：
sudo systemctl enable --now platform-worker-agent
```

## 6. 网络与最终验收

按新网段恢复 DNS、路由及必要的 NAT；不要直接重放旧网卡名。计算节点需能访问外部下载站，用户需能访问网站及 SSH NodePort，控制节点需能访问 worker 镜像代理和 Traefik NodePort；计算节点需能挂载 control NFS。K3s 节点间网络按所用 CNI 和安装文档开放。仅验证网页 HTTP 200 不代表完整平台可用。

```bash
sudo python3 scripts/platform_ops.py doctor --site /srv/platform-migration/target-site.json --backend /opt/computing-platform/current/backend
```

`doctor` 只读检查 API/数据库就绪、前端入口、节点 Ready、GPU 可分配、共享 PVC、数据库节点映射及个人镜像归档。随后用普通测试账号和管理员完成：

1. 登录、管理员加余额、费用到账；普通用户没有自助充值入口。
2. 申请一张 GPU，SSH 执行 `python -c 'print(6*7)'`，Jupyter 内核执行相同代码，并确认 GPU 设备可见。
3. 实例访问 PyPI/所需下载站，安装一个小型包；框架环境执行真实 CUDA 张量运算。
4. 在临时 `/workspace` 和持久 `/data` 分别写文件，保存个人镜像并释放。使用公共镜像重建后确认临时文件消失、个人文件保留；使用个人镜像重建后确认临时工作文件及系统环境按镜像恢复。
5. 多卡申请、多人争用单卡、重复提交及释放复用；已下架镜像不能通过旧编号重新申请。
6. 核对账户余额、历史订单、原个人镜像归属、监控和计费；需要时在专用测试账号验证预警及保存期。

实例验收会产生资源及真实内部计费，应使用专用测试账号，结束后释放测试实例。工具不默认申请 GPU，也不触发六小时回收测试。

## 回退

新平台未接收用户写入前，可保持新平台停止，恢复旧服务器的后端和代理并把访问入口指回旧站。新平台接收用户写入后，不能直接恢复旧 SQL，否则丢失新订单、余额和用户文件；应停两端并核对增量，再制定回退。不要让新旧后端同时管理同一数据库或对同一批用户同时计费。

## v0.7 专用数据卷补充

新环境先按 [数据卷与备份说明](../deploy/storage/README.md) 准备用户数据卷和计算节点运行卷，再执行原迁移入口。恢复后重新安装 root quota helper、初始化用户项目额度、复制镜像代理日志到 `WORKER_JOB_ROOT`。设置 bind mount 和 RequiresMountsFor 后验证重启挂载顺序。备份目的目录、NFS 来源授权、设备名、VG 名和用户 ID 均需按新服务器配置，不可照搬现场 IP。

日常在线备份使用 `scripts/backup_snapshot.py`；原 `platform_ops.py backup` 保持停机迁移语义。先用独立恢复工具验证有效备份，再按正式停机流程恢复。个人镜像 OCI 归档与数据库一起恢复；公共基础镜像仍需通过已有 export-images/import-images 流程导入新计算节点。

## v0.8 账号开通策略

不再配置 SMTP 注册服务。新站点首次管理员及管理端新建账号初始密码均为 password，用户可在账户设置修改。已有数据库恢复、升级或重复初始化保持既有密码哈希。旧 INITIAL_ADMIN_PASSWORD 配置不再用于新账号初始化。账号由管理端邮箱创建入口统一开通，角色可在创建后调整。
