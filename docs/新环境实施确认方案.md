## GPU 最小修复方案

已加载模块与当前内核磁盘模块：595.84；用户态 NVML：595.99.02，属于 Ubuntu 的 libnvidia-compute-595 包。APT 历史记录显示 595.84 → 595.99.02 的升级。已安装内核 7.0.0-38-generic 对应模块为 595.99.02，并存在 vmlinuz/initrd，GRUB_DEFAULT=0；系统有 reboot-required 标记。

直接原因是用户态库升级后仍运行旧内核及旧驱动模块。没有找到额外 NVML 副本、runfile 卸载器或 NVIDIA 安装日志；SSH 进程未设置 LD_LIBRARY_PATH/LD_PRELOAD。旧 550/580 包仍有记录，但是否为残留配置应结合 dpkg 状态判断，不能仅据名称卸载。

推荐在确认的维护窗口，先保存容器配置、restart policy、数据挂载清单，确认各作业 checkpoint 和容器是否可安全停止，然后受控重启计算节点进入已安装的 7.0.0-38 内核。无需先卸载或重装驱动。影响：10 个现有容器、桌面会话及所有在内存中的作业会中断；restart policy 不能保证训练进程恢复。

恢复方式：重启后验证 uname、模块版本、NVML、8 卡型号、原有容器及数据；若新内核启动失败，可经带外管理/本地控制台选择旧内核恢复主机访问。旧内核仍可能存在 NVML 不匹配，因此不能把回退内核视为 GPU 修复完成。执行前需要明确带外/现场恢复条件和维护窗口。

新平台验收还需 NVIDIA containerd runtime、device plugin、K3s allocatable、平台实例实际分配、PyTorch CUDA 运算及释放核对。现有 Docker 占用不受 K3s 调度器统计，必须先明确哪些 GPU 移交平台；默认不把 8 卡全部开放给 K3s。

## 待批准的挂载及共享配置

为保留 demo 的逻辑目录约定，拟采用：

- sdb1 → /srv/platform-system：公共镜像归档、可重建缓存、平台运行资源。
- sdc1 → /srv/platform-users：已有目录保持原位；新建专用 CPCloud 子目录存放新用户文件和个人镜像。
- /srv/platform-users/CPCloud/workspaces → bind /srv/platform-workspaces。
- /srv/platform-users/CPCloud/images → bind /srv/platform-images。个人镜像放用户盘，从而保持 demo “个人文件＋个人镜像共用 project quota”所需的同文件系统约束。公共镜像缓存仍在 sdb1。

确认后先进行只读挂载核验（不回放日志），检查无路径遮蔽或服务引用；备份 fstab 后才添加以下条目（此处为拟稿）：

```fstab
UUID=1e2b2833-949c-4b93-b156-f568ef11e8e3 /srv/platform-system ext4 defaults 0 2
UUID=7a4035c3-22d0-42d9-9326-612c94042bea /srv/platform-users ext4 defaults,usrquota,prjquota 0 2
/srv/platform-users/CPCloud/workspaces /srv/platform-workspaces none bind,x-systemd.requires-mounts-for=/srv/platform-users 0 0
/srv/platform-users/CPCloud/images /srv/platform-images none bind,x-systemd.requires-mounts-for=/srv/platform-users 0 0
```

sdc1 当前无 quota/project 特性。启用前需要检查 e2fsprogs、完整备份及文件系统状态，在该卷卸载时启用特性（可能需要 e2fsck 维护扫描），不能直接对在线卷修改。对 8 TB、有数百万 inode 的数据卷，扫描时间需评估。不会格式化、调整现有分区、移走旧数据或修改系统盘挂载。相关服务设置 RequiresMountsFor，避免数据盘未挂载时写入系统盘。

共享延续 NFS（不新增存储产品），仅允许实际内网客户端及经核实的来源地址访问；使用 sync、root_squash、专用服务 UID/GID，禁止旧脚本默认 no_root_squash。计算节点镜像挂载沿用 /mnt/platform-images；用户文件通过 K3s 的 RWX PVC 挂载，每实例只挂对应 user_ID 子目录为 /data。不得导出 sdc1 根目录和旧 minio/docker 目录。

## 推荐配额方案及需批准的功能适配

建议默认每用户 **100 GiB**（文件＋个人镜像共享），可调整；平台预留 **20%**，新建用户不改变已有额度。预计用户数尚未提供：100 GiB × 人数必须小于按实际可用空间、已有数据及预留量计算的可分配容量；暂不作容量保证。

固定额度便于用户预期和管理员规划。按实时用户数量平均分配会随新增用户缩小旧额度，可能使既有数据突然超限，不推荐。demo 当前实际为每用户占固定池的配置百分比，并非按用户数量动态均分；但依赖磁盘容量，扩容后会变化，而且默认 10% 对本盘过大。

实施需局部适配 demo 的 quota 模型、管理员调整入口和 root helper：保存固定字节额度，并使用 ext4 project quota 的块和 inode 硬限制执行，迁移时不覆盖原有数据。管理员增加额度前检查总承诺容量；容量不足时拒绝新用户存储分配/扩额，原有用户额度保持。达到个人或全局硬限制时内核返回 EDQUOT/ENOSPC，API 转为明确错误，保留已有文件。预留计算必须扣除 sdc1 已有数据与 ext4 保留块，不能直接用原 helper 的整盘百分比。

每用户 project ID 沿用 100000 + user_id；新服务使用核实未占用的数值 UID/GID，避免把已有 UID 1000 的历史数据计入平台全局 UID 配额。保留 demo 的 root 容器与 NFS subPath 方式时，权限隔离主要由后端鉴权、PVC 子目录和 NFS 客户端白名单保证；共享 UID 不等于恶意租户安全边界，网络中可达 NFS 的容器可能经用户态 NFS 客户端访问其他目录。若要求抵御恶意租户，需另行批准 per-user UID/GID、NFS 授权/网络隔离和容器权限调整，不能宣称现有方案已实现强隔离。

临时系统盘、/workspace 和下载缓存不属于 /data；实例释放时可以按 demo 回收临时盘，但持久 /data、个人镜像和删除用户后的资料均保留，清理另行确认。
