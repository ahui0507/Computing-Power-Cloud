# 用户数据隔离加固方案

日期：2026-10-16。后续状态：用户于 2026-10-17 授权实施，已完成部署与验收，见 [租户隔离加固与验收](租户隔离加固与验收-20261017.md)。下文保留原核查、设计和当时暂缓的背景。

## 目标和访问边界

普通平台用户只能通过文件接口、Jupyter、SSH/SFTP 和实验代码访问自己的个人文件及私有镜像。平台管理员、节点管理员和受控的镜像保存服务属于管理信任边界，不与普通租户等同。

容器只挂载 `/srv/platform-workspaces/user_ID`，在容器内呈现为 `/data`。`cd /data; cd ..` 应进入容器自己的 `/`，不应进入控制节点 `/srv/platform-workspaces`，也不应列出其他用户目录。允许访问容器本身的 `/usr`、`/opt`、`/workspace` 等环境路径，以维持 Python、Conda、CUDA、SSH 和软件安装功能；不采用 shell 别名或禁用 `cd` 作为隔离措施。

## 本次实测

使用指定的 campus-workbench:20261012 镜像创建两个临时 CPU 容器，分别只读挂载当时已禁用的验收账号 2、3 的个人子目录。不启用账号、不申请 GPU、不修改用户文件。镜像和 PVC 与平台相同；这是专门的挂载边界探针，不是完整的新实例业务验收。两账号及测试目录随后已按用户清理指令删除，详情见 [测试内容清理记录](测试内容清理记录.md)。

| 检查 | 结果 |
|---|---|
| 从 `/data` 执行 `cd ..` | 两个容器均进入各自 `/` |
| `/data/../user_另一用户` | 两边均不存在 |
| `/srv/platform-workspaces/user_另一用户` | 两边均不存在 |

| 验收账号 2 的既有持久化标记文件 | 账号 2 可见且哈希正确，账号 3 不可见 |
| 实际 `/data` NFS 挂载来源 | 分别为控制节点的 user_2、user_3 子目录 |

## 拟实施的局部加固

1. 保留现有 ext4、NFS、项目硬配额、容器 root 软件安装和个人镜像流程，不移动用户数据、不调整配额、不新增系统登录账号。
2. 在新建实例模板中禁用 ServiceAccount 令牌自动挂载；明确禁止宿主机网络、PID、IPC 共享、特权模式和额外主机目录挂载。移除不需要的原始网络能力，禁止提权；验证 SSH、Jupyter、包安装和镜像保存兼容性。
3. 为平台实验容器配置 Kubernetes NetworkPolicy。工作负载使用专用识别标签，并把标签及策略纳入创建、重试和归属检查；受控基础服务不作为租户工作负载处理。
4. 实验容器默认禁止直接访问平台管理内网、NFS、集群 API、Worker Agent、数据库、Redis，以及其他实例。允许受控 DNS 查询、公共互联网软件源及已核实的网站代理和实例 SSH 入站。具体 CIDR 和来源按现场网络核验生成，不能猜测；同时覆盖服务 ClusterIP、节点 IP、Pod IP 和实际启用的 IP 协议族。
5. 存储仍由宿主机 kubelet/NFS 客户端挂载自己的 subPath；容器不需要主动连接 NFS 服务器。镜像保存由节点服务执行，普通容器不持有它的认证信息。
6. 检查实际 CNI 策略执行效果。若原生 NetworkPolicy 无法封堵节点地址旁路，停止发布，不将 YAML 已创建描述为隔离已生效；提出具体节点防火墙补充规则，再依确认边界处理。

本方案不为普通用户开放节点 SSH、宿主机路径或 Kubernetes 管理凭证。不宣称能抵御宿主机 root 管理员、内核漏洞或完整容器逃逸；若需要此类强隔离，应单独评估用户命名空间或虚拟机等方案，并另行批准架构变更。

## 行为影响及确认原因

新规则会限制实验容器访问平台内网和其他实例。下载公共互联网软件包、单实例多卡训练应继续可用；同用户跨实例训练、校内私有 Git/对象存储/软件源可能需要单独批准的精确放行规则。不能默认开放整个校内网，否则可能重新打开存储旁路。

原始任务明确要求“改变功能行为”前提出方案并等待确认，因此在落实上述网络访问限制和权限收紧前请求确认。当前用户强调隔离要求已经授权核查和准备方案；本方案对现有内网通信方式的具体限制仍需要明确展示。

不重启节点、不修改磁盘挂载、不卸载驱动、不删除用户数据。现有实例的安全上下文无法原地修改；上线前先查活动实例，若需要重建会影响现有任务，则另行展示对象和影响并取得确认。网络策略先在两个专用测试工作负载上验证，避免直接作用于运行作业。
