# 租户隔离加固与验收（2026-10-17）

本轮按用户授权完成部署。新实例进入专用 `platform-workloads` namespace，默认禁止实例互访和直接访问管理内网，保留个人 `/data`、容器内 root、软件安装、GPU 训练、Jupyter、SSH/SFTP 和个人镜像保存流程。

最终 release：`20261017-isolation-bcd6e5ce03d9`，此前版本为 `20261017-https-fa4b01830e80`。完整服务器后端回归 **351 项通过**。本轮未迁移用户数据、数据库表或镜像仓库，没有重启节点、卸载驱动或重新构建公共镜像。

## 实际边界

### 网络

业务 namespace 中部署单一 `cpcloud-tenant-boundary` NetworkPolicy，选择所有 Pod，默认拒绝 ingress/egress；不会因漏掉某个租户标签而放行。

- Jupyter 入站仅放行 `kube-system` 中带 Traefik 标签的代理 Pod，端口 8888。
- 实例 SSH 入站仅放行控制节点 `192.168.24.64/32` 与其实际转发源 `10.42.0.0/32`，端口 22。后一个地址经实际抓包确认，未放行整个 Pod 网段。
- DNS 仅放行 `kube-system` 的 CoreDNS Pod，TCP/UDP 53。
- 公共互联网允许 TCP 80、443、22、9418；排除私有、环回、链路本地、CGNAT、组播及保留地址。
- 实例到另一实例的 Pod IP、Service IP、两个节点上的 NodePort，以及 NFS/RPC、集群 API、kubelet、镜像 Worker Agent 均已实测无法连接。

实测对照 Pod 在无策略时能连接 NFS、API 和 Worker Agent，证明被测服务真实可用。加入边界后连接被拒绝，DNS 与公网 HTTPS 软件源仍可用。

### IPv6 旁路

当前集群只分配 IPv4 Pod/Service CIDR，但 Pod 仍有 IPv6 链路本地地址。测试中，即使 IPv4 NetworkPolicy 已生效，另一个 Pod 的 IPv6 监听服务仍可连接。因此本轮在两个节点安装 `cpcloud-pod-ipv6-guard.service`：

- 通过 `ip6tables` 的独立 `CPCLOUD-POD-IPV6` chain，丢弃从 `cni0` 进入 INPUT/FORWARD 的 IPv6 流量。
- 开启网桥 IPv6 netfilter 检查，使同机桥接流量也经过规则。
- 不修改主机管理网卡、SSH 入口或 Pod 内的 IPv6/IPv4 loopback；单实例多进程训练的本地通信不受影响。
- service 在 k3s/k3s-agent 启动前应用规则，并作为节点服务依赖；两个节点已启用，安装过程未重启节点服务。

验收使用真实 IPv6 监听服务：Pod 内 `::1` 可连接，另一 Pod 在加规则前可连接，加规则后超时；生产 namespace 中再次验证 IPv6 跨实例连接被阻断。当前不支持 Pod 的外部 IPv6 通信；以后启用双栈必须先部署完整 IPv6 策略并重新验收，不能直接撤掉 guard。

### 权限与凭据

- Pod 使用专用、无业务 RBAC 授权的 `platform-workload` ServiceAccount；Pod、专用 SA 和业务 namespace 的 default SA 均禁止自动挂载集群凭据。
- 关闭 hostNetwork、hostPID、hostIPC、共享进程 namespace 和 Service 环境变量注入。
- 保留容器内 root，设置 `privileged=false`、`allowPrivilegeEscalation=false`、`seccompProfile=RuntimeDefault`。
- 先移除全部 capability，只保留 SSH、文件操作和包安装所需的 CHOWN、DAC_OVERRIDE、FOWNER、FSETID、KILL、SETGID、SETUID、SETPCAP、NET_BIND_SERVICE、SYS_CHROOT、AUDIT_WRITE。未授予 NET_RAW、NET_ADMIN、SYS_ADMIN、SYS_PTRACE、SYS_MODULE 或 MKNOD。
- 实际进程显示 `NoNewPrivs=1`、`Seccomp=2`；原始套接字创建被拒绝，集群凭据路径不存在；专用 SA 读取 Secrets、创建 Pods 的 RBAC 检查均为 no。

### 存储与创建检查

生产 namespace 使用新的 Retain PV/PVC 对现有 NFS 后端建立绑定，继续仅挂载 `user_ID` 子目录到 `/data`。这是存储引用的调整，不是数据复制；已有目录、硬配额和同账号共享存储语义保留。

创建实例前，后端检查 namespace 标记与 Pod Security baseline、专用 SA、实际 NetworkPolicy 摘要，以及节点 guard 标签。缺失、被修改或出现额外可叠加的网络策略时拒绝创建，不先创建一个无保护的 Pod。生产 SHA256 为：


创建重试还会核对已有 Pod 的凭据挂载、能力、seccomp、host namespace、卷来源和全部挂载路径。额外挂载整个 workspace PVC、挂载其他用户的认证 Secret或增加危险权限的 Pod 均拒绝接管，保留对象等待管理员核对。

## 业务影响

用户可以继续在自己的实例中使用 root、sudo、Conda、pip、dpkg、CUDA、Jupyter 和 SSH。公共 HTTPS 软件源与 Git 常用端口可用，单实例多 GPU 通信可用，个人镜像由受控节点服务保存。

默认阻止同账号或不同账号的跨实例网络通信、校内私有 Git/对象存储/实验服务，以及实例直接调用位于内网的平台接口。确需访问时，按具体身份、目的地址和端口审核白名单；不要开放整个校内网或通过额外宽泛 allow policy 绕过基准策略。策略调整需同步后端摘要，并处理冻结了旧摘要的待创建申请。

## 隔离级别

本轮完成容器、网络和挂载边界加固。NFS 仍采用 AUTH_SYS 与现有共享 UID/GID；它们没有被当作独立的恶意租户身份认证机制。本轮依靠每用户子目录挂载和封堵直接 NFS 访问关闭已发现旁路。

容器仍共享宿主机内核和 GPU 驱动，节点管理员属于可信管理边界；本轮不等同于虚拟机级隔离，也不保证抵御内核或驱动漏洞。面向完全互不信任的外部租户，应进一步评估 GPU 虚拟机、独立节点及具备身份认证的存储方案。
