# HTTPS 入口可行性核查（2026-10-17）

后续状态：用户选择使用内网 IP，现已完成部署，参见 [HTTPS 部署与验收](HTTPS部署与验收-20261017.md)。下文保留切换前的核查依据。

结论：现有网络转发可以承载 TLS，补 HTTPS 的服务器配置可以自行完成，不需要为此新增 443 映射或修改上游转发。正式浏览器可信访问仍需可用域名与对应证书，或由客户端信任的校内 CA 证书；是否需要校方协助取决于这些资源的管理权限。本次仅核查，没有启用 HTTPS 或修改运行配置。

## 实测依据

- 外部入口为 `10.72.63.42:64022`，控制节点地址为 `192.168.24.64`。
- 控制节点 HAProxy 以 TCP 模式监听 22，在同一入口识别 HTTP 和 SSH。HTTP 转到 Nginx `127.0.0.1:8081`，携带 PROXY v2 来源信息；其他流量默认转到 SSH `127.0.0.1:2222`。
- 从当前客户端发送标准 TLS ClientHello，在控制节点 `eno1` 上用 ClientHello 中唯一的随机标记过滤，仅观察本次测试包。实测它原样到达 `192.168.24.64:22`，来源为 `10.240.52.192`，TCP 载荷 517 字节。
- 当前 TLS 请求收到 SSH banner。这与 HAProxy 未配置 TLS 分支、未知协议进入 SSH 后端一致，证明当前失败点在本机协议分流配置。
- Nginx 配置检查通过，未配置 TLS listener、业务域名或证书。平台 `INGRESS_USE_TLS=false`，`INGRESS_HOST=10.72.63.42:64022`。常见证书目录未发现已部署业务证书；系统 CA 信任库不能作为网站服务端证书使用。
- HAProxy、Nginx、SSH、平台后端均为 active。

核查记录：本地 `.ops/https-entry-preflight.json`、`.ops/https-entry-tls-probe.json`。抓包仅匹配本次测试 TLS 握手标记，没有记录业务请求或认证内容。

## 可自行实施的部分

在 HAProxy 增加 TLS ClientHello 分支，透传至本机 Nginx 的独立 TLS listener；Nginx 使用网站证书终止 TLS，继续代理网站、API 和 Jupyter WebSocket。HTTP、TLS、原生 SSH 继续复用现有外部 64022 端口，现有 SSH 管理地址不需要迁移。

当前 HTTP 分支限制来源 `10.240.0.0/16`，TLS 分支需保留相同访问范围。还需同步平台 HTTPS 链接、CORS、SSH relay 的 TLS 路径和客户端信任，验证 Jupyter、WebSocket、原生 SSH/SFTP、现有实例访问与 HTTP 跳转，预置回退配置后再切换。

## 需要补齐的资源

1. **已有自主管理域名**：可将域名解析到当前入口 IP，通过 DNS-01 申请公共可信证书。网站继续使用 `https://域名:64022`；DNS-01 不要求开放公共 80/443，也不要求公共互联网能访问此内网平台。
2. **使用学校域名**：通常需域名管理员提供解析与证书，或提供 DNS-01 验证能力。需要的是域名/证书协助，并非重新配置算力服务器的端口转发。
3. **继续使用内网 IP**：常规公共 CA 不会为此私有 IP 签发证书。可由校内 CA 或自签名证书覆盖该 IP，但客户端需要建立相应信任；单纯安装自签名证书不能让所有浏览器自动信任。

本机当前配置未显示已用业务域名，不能据此判断学校或用户是否另有可用域名、证书或 DNS 管理权限。该资源需在正式实施前确定。
