# 算力附带个人存储部署与验收（2026-10-18）

用户要求在 GPU 申请时附带存储，并按八人使用评估额度。已上线 `20261018-bundled-storage-v1`，基于当时线上 `20261018-scratch-watchdog-v2` 制作局部增量。

## 容量依据

控制节点数据卷 `/dev/sdc1` 总容量约 7.22 TiB；已有历史数据、ext4 保留块和 20% 空闲预留继续保留。平台冻结的用户存储池为 `3,383,530,276,455` 字节，约 3,151 GiB；审计时预留之外可用空间约为同一数值，不应把整卷容量当成新平台可分配容量。

采用每账号默认 **300 GiB**：八个账号共承诺 2,400 GiB，剩约 751 GiB 用于管理员调整额度和后续需求。每人 400 GiB 时八人合计 3,200 GiB，已超过当前池，因此不采用。

八张 GPU 限制同时获得 GPU 的用户数，不能限制长期保留文件的历史账号总数。存储池账本对所有已承诺配额检查容量，新增账号不足时拒绝，不通过超售保证“每人 300 GiB”。默认额度也不是立即写满或预填充文件。

## 申请行为

- 创建页标明“GPU 算力＋个人持久存储”，显示真实总额度、已用量和额度内剩余空间，按钮为“申请算力与存储”。直接申请和排队申请使用同一账号额度。
- `/data` 为账号持久空间；同账号多卡、多实例和重复请求共享同一额度，释放实例继续保留文件，个人文件与保存的镜像合并计量。
- 原每 GPU 40 GiB 临时盘继续单独计量，不增加持久存储额度。页面分别解释 CPU/内存份额、临时盘、账号持久存储。
- 新账号默认 `DEFAULT_STORAGE_LIMIT_GIB=300`。申请结果返回 `persistent_path`、`storage_scope=user` 和有效的 `personal_storage_limit_gib`，不会让普通用户自行绕过管理员配额。
- 后端继续在 GPU 预留和订单创建之前确认账号文件系统配额；存储池容量不足时，不先占用 GPU。

原有效账号 1、4 的冻结默认值及实际 project hard quota 从 100 GiB 向上调整为 300 GiB，两者共承诺 600 GiB，文件数量和字节使用量未改变。仅匹配“有效账号、无自定义覆盖、原冻结默认值和内核额度均为 100 GiB”的记录。其他账号及自定义限额保持原值。调整进入审计记录，不删除文件，不重建用户目录。发布切换和配额更新约 8.7 秒。

- Linux 后端 361 项测试通过，包含共享额度、幂等重放、释放后保留额度、管理员自定义值及池容量不足时无 GPU/订单副作用。
- 前端 46 项测试、TypeScript 检查和生产构建通过。真实浏览器验证：300 GiB 总额度、50 GiB 已用与250 GiB 剩余显示正确，选择两卡后临时盘变为80 GiB，个人存储仍300 GiB；提交后进入实例列表。
