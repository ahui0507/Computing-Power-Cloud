## 测试条件与证据边界

物理设备为八张 A100 PCIe 40GB。测试仅将各单 GPU IOMMU group 临时切为 identity；非 GPU 域、ACS、驱动 595.99.02、内核 7.0.0-38-generic 和公共镜像均未改变。各组按现场 inventory 核对，而非假定 group 编号永久不变。

PyTorch 双卡选用物理 GPU 6/7，四卡选用 0/1/6/7，覆盖两个 NUMA 域；八卡测试覆盖全部设备。TensorFlow覆盖双卡与八卡，每轮训练均在单一 Python 进程中使用 MirroredStrategy，恢复则另起新容器和 Python 进程。

本轮使用受信任的管理员诊断容器，分别加载现有 PyTorch/TensorFlow 开发镜像；没有修改租户 Pod 或挂载用户数据。诊断容器使用 host network，仅以 loopback 进行 NCCL bootstrap，并提供独立 1 GiB /dev/shm；移除常规 Linux capabilities、启用默认 seccomp。没有验证通过网站分配的实例撤销兼容参数后的访问流程，因此不能把本轮称为网站正式发布验收。

测试显式设置 `NCCL_P2P_DISABLE=0`，未强制 NCCL 拓扑阈值或通信算法。实际日志均含 `via P2P` 传输记录；跨 NUMA 路径由 NCCL 按默认拓扑选择 P2P/SHM 等传输，未声称每个 NCCL 通道都走 P2P。TensorFlow 压力测试在 replica context 中执行 all_reduce，避免 host destination 导致归约退回 CPU。

已检验正确性和短时持续运行；不是正式吞吐基准，也不替代长时间训练、生产规模模型、并发租户或重启后的验证。该机器没有活动 NVLink，不应描述为 NVLink 性能恢复。

## 验收脚本修正

第一次 PyTorch 双卡恢复的参考比较失败，记录保留为 `torch2-resume.json`。原因是验收脚本给两个优化器加载同一份 checkpoint，CPU Adam step Tensor 被共享，两个 step 操作改变了参考计数。修正为各自深拷贝状态，并增加存储独立性检查；原校验容差保持不变。双卡恢复重跑及随后四卡、八卡恢复全部通过，成功重跑记录为 `torch2-resume-attempt2.json`。未将这次脚本误报计为硬件验收成功。

TensorFlow 首次双卡脚本在执行训练前因严格设备放置失败，记录保留为 `tensorflow2.json`：compute_average_loss 的内部断言包含 GPU 不支持的字符串常量。改为等价的全局批次归一化表达式，并将压力校验断言的标量 verdict/字符串诊断显式放到 CPU，完整张量比较和 NCCL 归约仍在 GPU，保持 soft device placement 关闭。

第二次双卡检查已建立原生 NCCL/P2P，但默认 A100 TF32 矩阵乘法的输入舍入与 NumPy FP32 参考值产生约 7.3e-5 的梯度差异，记录保留为 `tensorflow2-attempt2.json`。为统一计算精度，仅在验收进程关闭 TF32，维持原有 FP32 参考值和容差；成功重跑记录为 `tensorflow2-attempt3.json`。本轮正式参考比较均使用 FP32，不是混合精度或 TF32 的数值精度验收，公共镜像默认精度设置未改变。
