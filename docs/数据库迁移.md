# 数据库版本迁移

数据库结构由 `backend/alembic/versions` 维护，ORM 表定义是开发时生成迁移的依据。`database/schema.sql` 保留为历史设计参考，安装脚本不再导入它，也不再通过 `create_all` 维护线上结构。

## 新数据库

先创建 MySQL 数据库及账户，配置 `backend/.env` 中的 `DATABASE_URL`，然后在后端环境运行：

```bash
cd backend
python scripts/init_db.py
```

此命令先升级到最新版本，再幂等创建角色、GPU 类型、管理员和默认种子数据。单独执行结构迁移可使用 `alembic upgrade head`。

`0001_initial_schema` 是包含 21 张表的冻结基线，后续修改 ORM 必须另建迁移。`0002_enum_values` 将历史 ORM 写入的大写状态统一成小写业务值，与接口和原 SQL 设计一致。

`0003_workload_runtime` 增加申请时价格、镜像启动路径和实例状态说明。初始化支持 MySQL 命名锁，多个副本不会同时执行迁移和种子写入。新数据库只登记可构建的 Jupyter 测试镜像，默认管理员使用指定密码或持久化随机密码。

`0004_recoverable_operations` 增加 `allocation_operations`，保存创建/释放意图、执行租约、失败信息与重试时间；申请增加参数摘要、计费截止时间、首次就绪时间和状态核对时间。历史 `active` 申请回填首次就绪时间，历史 MySQL 原生申请状态 ENUM 转为 VARCHAR，支持 `releasing`。

升级到 v0.1.1 时先备份数据库及共享目录，执行 `alembic upgrade head` 后再启动新后端。后台可为缺少操作记录的旧待创建申请补齐记录，并为有预留的失败/停止申请安排清理；无法确认归属的集群对象保留等待核对。降级迁移会删除操作与截止时间信息，并把 `releasing` 映射为 `failed`，因此恢复旧源码前必须先完成或核对所有进行中的操作。

## v0.5.0 套餐迁移

`0009_prepaid_packages` 在 `0008_personal_image_history` 基础上增加套餐冻结金额、付款时间、到期时间和退款时间，将计费模式统一为 VARCHAR 以支持 `day`。已有以 `container-` 开头的实例展示名称回填为显卡简称与上海时区创建时间，同一用户同一分钟的重名追加序号；申请编号、路由标识、所属用户及账单金额不变。

升级前备份数据库、运行时配置和当前发布指向，先在生产数据库副本上执行迁移并核对金额、余额、归属及实例标识。现场备份在 `/srv/platform-backups/plans-20261011/`，副本演练结果见 [迁移验证记录](validation/2026-10-11/plans-schema-rehearsal.json)。不要直接用全库备份覆盖升级后的新增订单。

当前现场数据库保留了更早版本的 `allocations.ssh_password`、`allocations.jupyter_token` 列和部分旧字段注释，未过滤的 `alembic check` 会报告这些既有差异。本轮迁移保留这些列，逐项核对后仅允许上述已知差异，新套餐字段与 ORM 一致；新部署不要据此跳过未知的结构差异。

兼容旧账单中的 `on_demand` 计费值，读取时保留原金额。已有任意已付款套餐后，`0009` 降级会拒绝执行，避免丢失扣款、到期和退款状态。此时修复应向前发布；需要恢复旧环境时，应独立核对完整数据库及用户数据的恢复点。

## v0.6.0 计算配额迁移

`0010_compute_quotas` 增加 `allocations.cpu_cores`、`ram_mb` 和 `compute_reserved`，分别保存申请时冻结的逻辑 CPU 配额、内存 MiB 和是否仍有计算预留。已有历史订单的 CPU/内存保持 NULL，不能把过去未实施的限制回填成已生效配额。

旧待创建、运行、释放中或仍持有 GPU 的申请会标记为仍有预留。旧实例未设置 CPU/内存上限，因此其所在节点在释放完成前保守地停止接受新申请，保留原实例运行。新实例通过已冻结的创建参数设置 Kubernetes requests/limits；配置调整不会改变旧订单。

有 `compute_reserved=1` 的记录时降级会拒绝执行。升级前在副本核对结构、标识、余额、账单，并验证并发分配；现场备份为 `/srv/platform-backups/compute-20261011/`。迁移保留既有旧凭据列及注释差异，核对方式与 v0.5.0 相同。不得用旧全库备份覆盖升级后的新订单。

## v0.6.1 比例配额迁移

`0011_proportional_compute` 增加 CPU 毫核字段 `cpu_millicores` 和比例分母 `node_gpu_count`。旧固定配额只做等价的 CPU 单位转换，原 `cpu_cores`、内存、预留状态、余额和账单均保持原值；旧订单分母保持 NULL，不伪造历史比例。

新比例订单在选定并锁定节点后，根据其硬件容量、系统预留百分比和登记 GPU 总数计算，保存实际限制与分母，后续重试和回收使用冻结值。已有比例订单后降级会拒绝删除相关字段，即使订单已经结束，以免丢失历史精度和份额。升级前备份位于 `/srv/platform-backups/ratio-20261011/`，副本核对继续仅允许已知旧注释及旧凭据列差异。

## 已有业务数据库的接入步骤

已有数据库可能由历史 SQL 或 ORM 建表，必须先在副本上核对表、字段、索引与外键。不能直接重放初始建表迁移；初始化命令遇到这种情况会失败并停止部署。

在确认现有结构与初始基线一致后，标记该基线，再运行后续迁移：

```bash
cd backend
alembic stamp 0001_initial_schema
alembic upgrade head
alembic check
```

`stamp` 只标记版本，不修改表结构，也不会修复差异。如果结构不同，应先在副本上形成并验证补齐差异的迁移，再接入基线。原生 MySQL ENUM 与基线 VARCHAR 的类型差异也需要核对；不要仅根据表名相同就标记基线。

## 开发流程

```bash
cd backend
alembic revision --autogenerate -m "describe schema change"
alembic upgrade head
alembic check
python -m pytest
```

提交前检查自动生成迁移的具体 SQL 和降级行为。已有迁移不随 ORM 修改而重新生成。测试会验证空库升级后的结构与 ORM 一致，并验证历史大写状态转换。

## v0.7 存储份额与提醒迁移

`0012_storage_and_notices` 为 quotas 增加可空的 `storage_share_percent`，NULL 继承平台默认份额；创建按用户和去重标识唯一的 notices 表。既有余额、账单、订单和资源分配不改写。安装数据卷及原生 quota helper、初始化用户目录后，才启用 `STORAGE_QUOTA_ENABLED`。旧客户端省略存储字段时保留已有自定义值，明确传 NULL 才恢复默认。

升级前保留有效备份，并使用 `verify_backup_recovery.py --backend 新版后端路径` 演练隔离数据库升级与 API 读写。同一迁移版本内回退代码可保留新增表列；跨迁移版本回退需同时核对旧版健康检查和数据库版本，不能只切换发布链接。确需 downgrade 时先完成独立备份，避免丢失提醒及自定义存储份额。
