## 2. 临时磁盘缺少每实例限额：优先处理

线上 Pod 构造资源只设置 GPU、CPU、内存，没有 `ephemeral-storage` 的 requests/limits。`/dev/shm` 有 1 GiB 限额，但普通运行卷没有 sizeLimit，分离存储布局的 `/workspace`、`/tmp` 和容器可写层也没有对应的临时盘预算。

已核验 `platform-workloads` 没有 LimitRange 或 ResourceQuota，也没有 mutating admission webhook 为 Pod 补充默认限制。持久化 `/data` 的 filesystem quota 不约束这些节点本地写入。

计算节点 nodefs/imagefs 使用同一容量池，本次查询仍有约 609 GiB 可用，并未磁盘满。kubelet 的 nodefs/imagefs 驱逐阈值均为剩余 5%；目前主要依赖节点压力驱逐，而非每实例的临时空间上限。用户下载大模型到默认缓存、安装软件、写训练临时文件时，可能消耗同机共享空间并影响其他实例。

建议：根据节点保留空间和 GPU 配额确定临时盘预算，给 Pod 设置 requests/limits 和适当的 emptyDir sizeLimit；配合容量/inode 告警、容器日志与镜像清理。限额触发通常导致驱逐而非文件系统硬阻止写入，必须验证测量和驱逐行为，并明确告知用户哪些目录会丢失。

依据：[Pod 构造](../backend/app/infrastructure/kubernetes/manifests.py)，以及本次 namespace、kubelet configz 和 stats/summary 只读检查。

## 3. 后台任务与故障告警依赖同一后端：优先补可观测性

定时释放、欠费处理、资源状态核对、排队调度和站内告警都由 FastAPI lifespan 启动的同一个 reconciliation 周期执行。循环中各批处理顺序运行，慢的集群调用或异常会拖长后续周期。已经有操作租约、重试、幂等结算和持久化截止时间，不应据此声称存在必然重复扣费；风险主要是资源回收、排队和通知延迟。

当前 `/health` 检查数据库连接、迁移、表和初始角色，不核对上述后台循环最近成功时间。API healthy 不足以证明定时释放正在执行。站内告警通过该后端写入 Notice；后端或数据库自身中断时，告警刷新也受影响。两个节点的系统服务中未发现独立 Prometheus/Alertmanager/Zabbix 等组件；未检查平台之外是否有第三方监控。

建议：记录后台循环的独立心跳、耗时、最近错误、最老待处理项及超时释放数量；让关键回收任务具备独立执行和优先级，再由平台之外的监测渠道发送必要的故障通知。

依据：[应用生命周期和健康接口](../backend/app/main.py)、[后台循环](../backend/app/services/reconciliation_service.py)、[站内告警](../backend/app/services/operational_alert_service.py)、[就绪检查](../backend/app/services/readiness_service.py)。

## 4. 控制面与存储存在单点：架构限制

当前只有一个控制节点 dell 和一个计算节点 ubuntu。控制节点同时承载入口、后端、MySQL、K3s 控制面和 NFS；计算节点的用户目录从 `192.168.24.64:/srv/platform-workspaces` 挂载。

控制节点故障会同时影响登录、调度、站内告警和持久文件访问。已经在 GPU 内存中运行的程序不一定立刻停止，但依赖 NFS 的读取和 checkpoint 写入会受影响，不能保证任务继续正常运行。单个文件系统中的多个目录也不是独立故障域；本次没有把 `/dev/sdc1` 误认为已确认的单块物理硬盘或判断 RAID 状态。

可按实际可用性目标评估存储独立、控制面冗余和数据库高可用。仅增加前端或 API 副本不能解决共享存储与数据库单点。

## 5. 面向完全不可信租户的隔离边界：使用范围限制

已部署的 namespace、默认拒绝 NetworkPolicy、IPv6 guard、禁止提权、受限 capabilities、seccomp、存储访问检查等继续有效，本轮配置也未撤销这些边界。

当前仍共享宿主机内核，NFS 使用 `sec=sys` 和共享映射 UID/GID；GPU 专用 identity 则按用户选择取消对应 GPU 的 DMA 地址翻译保护。这些条件限制了可承诺的隔离级别。

建议：按受控内网协作的信任模型运营；扩大到完全不可信外部租户前，评估独立节点/虚拟机、GPU 分配方式及存储身份认证。不要把现有容器和网络边界表述为等同于独立虚拟机的硬件隔离。

依据：本次 NFS exportfs、GPU 启动检查和此前 [租户隔离验收](租户隔离加固与验收-20261017.md)、[GPU 正式修复](GPU-IOMMU正式修复与验收-20261018.md)。

## 6. 训练进程的故障恢复仍依赖用户程序：能力限制

容器可以重启，但平台任务 runner 和 SSH/Jupyter/tmux 中启动的训练没有通用的自动 checkpoint、自动重新启动或跨节点恢复协议。当前本身也只有一个 GPU 节点。

释放前检查只覆盖平台登记的后台任务和镜像保存，未完整扫描所有 SSH/Notebook/tmux 进程。界面已经明确提示这一范围；这属于覆盖范围限制，不能说成释放操作完全没有提醒。

建议：提供进程与 Notebook 会话可见性，继续引导 checkpoint 写到 /data；若要提供托管训练任务，则进一步定义 checkpoint、失败重试和恢复协议。

依据：[任务 runner](../backend/app/services/job_service.py)、[释放检查](../backend/app/routers/resource.py)、[实例界面](../frontend/src/components/InstanceList.vue)。

## 7. 长时负载与收费故障场景：验收缺口

原生多卡已有功能、恢复、短时压力和真实平台接入验收，但不是数小时/数天的满载、并发租户及存储压力验收。一次 CUDA 初始化失败尚未确认原因；之后完整重测、40 个初始化进程和三次八卡示例启动通过，不能据此断言该事件根因已修复。

线上目前有一条正价申请和一条正价结算记录，不能说完全没有计费验证。最近的 GPU 验收都是零费率，需要进一步演练真实价格下的余额耗尽、后台重启、网络中断、延迟释放、包时失败退款和重复请求。现有单元测试与历史成功记录不等同于全部生产故障场景已完成演练。
