# 通用多卡通信修复方案（2026-10-17）

最新状态：已按用户要求完成 [GPU IOMMU 正式修复与重启验收](GPU-IOMMU正式修复与验收-20261018.md)。生产八卡已持久化 identity，新实例默认原生 NCCL，TensorFlow 新示例默认单进程；8/8 GPU 可用。网卡/存储等其他域及既有网络、容器隔离保留。保留一条未确认原因的 CUDA 初始化失败记录，后续 40 个初始化进程和 3 次八卡示例启动通过，详见正式记录。

前期证据：[两卡 A/B/A](两卡IOMMU对照验收-20261017.md) 与 [八卡临时验收](八卡原生通信临时验收-20261018.md)。下文为正式上线前的历史方案，不代表当前仍使用 DMA-FQ。

用户先要求确认是否确实为 IOMMU 瓶颈，并评估 passthrough、延迟失效、批量映射与 DMA buffer 复用，随后明确批准“允许两卡临时 A/B，测完恢复”。授权仅覆盖两卡临时因果验证及恢复，不包含八卡正式变更、持久化或重启。下文保留方案与验证前的证据边界，正式验证结果以最新验收记录为准。

## 已确认的故障

8 张 A100 PCIe 40GB 使用驱动 595.99.02、内核 7.0.0-38-generic。全部 GPU 各自属于单设备 IOMMU group，当前默认域为 DMA-FQ，PCIe 上游 ACS 重定向开启。没有活动用户实例、GPU 计算进程或运行中的 QEMU/libvirt 虚拟机。

在正常平台分配的八卡零费率实例中编译独立 CUDA 检验器，完全不依赖 TensorFlow 或 PyTorch。GPU 0 向 GPU 1 复制 8 MiB，CUDA API 返回成功，但 **2,097,152 个 uint32 全部不匹配**。首个值应为 999480348，读回 4294967295。该故障与内核中的 GPU DMAR DMA Write fault、PTE Write access is not set 对应，不能通过单纯修改训练代码解决。

基线验收实例 `container-30-651e9019` 已释放，费用 `0.0000`，8 张 GPU 恢复空闲。未写入管理员 `/data`。

## 可审查的拟实施步骤

1. 在控制面将计算节点置为 maintenance 并 cordon，确认没有申请、实例或 GPU 客户端。停止 GPU 设备插件和持有 GPU 的监控/持久化服务，保存原状态。
2. **先仅处理 GPU 0/1**，对应 `0000:3d:00.0`、`0000:3e:00.0`，IOMMU groups 14/15。保存原 DMA-FQ 类型，解绑 NVIDIA 驱动，将这两个单 GPU group 切换到 identity，再重新绑定驱动。
3. 用同一 CUDA 二进制复验双向复制。若失败，恢复原 DMA-FQ 域和驱动绑定，不继续扩大。
4. 仅在验证成功后，将相同步骤扩展到另外六张 GPU；检验 8 卡全部 56 个有向复制组合，验证默认 P2P 的 NCCL 与 TensorFlow 单进程 MirroredStrategy。
5. 确认无新增 DMA/Xid 错误、GPU UUID/索引一致、节点及既有租户隔离正常，再持久化 GPU 专用配置并恢复申请。若驱动无法正常热重绑，可能需要在维护窗口重启计算节点以恢复；控制节点和网站不重启。

全程不调整 NIC、RAID/存储或其他 PCI 设备的域，也不关闭全局 IOMMU、不修改 ACS 寄存器。实际候选 GPU groups 为 14、15、18、19、27、28、29、30；每组都只有对应一张 GPU。

执行脚本默认只读：[switch_gpu_domains.py](../deploy/gpu-peer/switch_gpu_domains.py)。真正切换需要显式 `--execute`、刚核验的维护状态证明和回退记录路径。脚本核对厂商、设备类型、单设备组和 GPU 客户端，失败尝试恢复原域及绑定，并核对其他设备的域未改变。

## 必须确认的保护变化

Linux 官方 ABI 将 identity 域定义为：设备 DMA 不再经过 IOMMU 翻译，`Maximum performance but zero protection`。因此这不是无风险调优：**八张 GPU 的 DMA 硬件保护会降低**。已部署的 namespace、NetworkPolicy、IPv6 guard、容器权限、GPU 设备分配与文件挂载边界继续保留，但不能代替 GPU DMA 保护。

此前 [多卡通信兼容方案](多卡通信兼容方案.md) 明确要求“涉及重启或隔离变更时单独确认”。本次请求修复通用多卡通信，仍需对这个新发现的硬件保护取舍作出明确选择，不能把它当作普通软件参数静默切换。

若必须保留当前 GPU DMA 翻译保护，暂不实施此硬件方案；需要继续采用软件通信回退或评估受支持的 GPU 虚拟机/VFIO 路线，不能宣称原生 PCIe P2P 已恢复。

## 已准备的框架验收

`deploy/gpu-peer/verify_torch_collectives.py` 使用原生 NCCL 进行 DDP 训练，与全局批次参考梯度、权重和 Adam 状态比较，逐 rank 检查权重与优化器状态一致，并逐元素校验 8 MiB 图案张量的重复 all-reduce。计划分别覆盖 2、4、8 卡；再次启动程序时使用 `--resume` 验证 checkpoint 恢复后的训练。

`deploy/gpu-peer/verify_tensorflow_mirrored.py` 验证单进程 MirroredStrategy + NcclAllReduce，与 NumPy 计算的全局批次参考梯度和带 momentum 的 SGD 更新比较，检查全部 GPU 上的权重与优化器状态，并验证 8 MiB 图案张量归约及独立程序重启后的 checkpoint 恢复。

这些脚本均拒绝 `NCCL_P2P_DISABLE=1`，防止把兼容路径当作原生路径验收成功。目前仅完成 Python 语法检查，尚未运行修复后框架验收，不能据此宣布 P2P 已恢复。

再次只读核验：计算节点未 cordon，GPU 插件只在 `nvidia.com/gpu.present=true` 节点运行；当前无用户 GPU 任务，GPU 文件客户端仅设备插件。维护时须停止插件、监控和持久化服务并重新检查客户端；现有 IPv6 guard 及其 k3s 依赖保持启用。

## 延迟失效与缓冲区复用的现场对照

内核配置为 `CONFIG_IOMMU_DEFAULT_DMA_LAZY=y`，启动日志同时记录 `Default domain type: Translated` 和 `DMA domain TLB invalidation policy: lazy mode`。八个 GPU group 当前仍为 `DMA-FQ`。Linux 官方 ABI 说明 DMA-FQ 已使用 batched invalidation；这与批量建立映射是不同概念，不能混为一谈。

通过实际平台双卡实例 `container-31-dcbd145d`，在 TensorFlow 镜像中编译并执行 `deploy/gpu-peer/diagnose_dma_paths.cu`。分配到物理 GPU 6/7（`0000:b4:00.0`、`0000:b5:00.0`）。GPU source/target 与 pinned host buffers 均只分配一次，循环复用；每次写入不同图案，避免旧数据误判。源到目标双向分别覆盖 256 B、4 KiB、8 MiB，每种大小重复三次。

| 路径 | 逐字校验通过 | 逐字校验失败 |
| --- | --- | --- |
| 显式 pinned host 中转（D2H + H2D） | 18 | 0 |
| cudaMemcpyPeer，已启用 peer access | 0 | 18 |

P2P 每一例都返回 CUDA 成功，但对应的全部 uint32 数据不匹配；8 MiB 一例为 2,097,152 个字全错。测试时间窗口内新增 GPU `b5:00.0` 的 `DMAR: [DMA Write NO_PASID] ... PTE Write access is not set`。测试实例已释放，费用为零，8 卡恢复可分配。

结论边界：这是已复现的 **P2P 数据正确性故障**，不能仅称为 IOMMU 吞吐瓶颈。当前已启用 lazy/batched invalidation，复用现有 CUDA buffer 也未消除故障。尚未在驱动层实现或测试批量建立 DMA 映射，不能声称排除了所有映射优化；该工作属于 NVIDIA 驱动/内核映射路径，不能用增加 CUDA batch size 等同替代。

`iommu=pt` 对应 `iommu.passthrough=1`，Linux 官方参数文档定义为默认让 DMA bypass IOMMU。它与关闭整个 IOMMU 并不相同，但对进入 identity 域的 GPU 仍取消 DMA 地址翻译保护，而且全局参数会影响更多设备，不应当作保持 DMA 隔离的优化。

上述验证前证据与 NVIDIA CUDA 12.5.1 文档中的 Linux 裸机 IOMMU/P2P 限制一致。当时尚未做域切换 A/B；随后获准实施的两卡 A/B/A 已确认 identity 下全部正确、恢复 DMA-FQ 后故障重现。该结论限定于当前驱动/PCIe 拓扑和已测两卡，不代表八卡全组合或框架验收已完成。持久化、扩展八卡与重启仍需另行决定。
